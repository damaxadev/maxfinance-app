# RISKS.md — Riesgos técnicos

- **Seguridad multi-tenant**: reglas de Firestore mal configuradas podrían filtrar datos entre usuarios o grupos. Mitigación: probar las reglas con el emulador de Firebase antes de cada deploy, no solo confiar en la lógica del frontend.
- **Neteo de deudas**: el algoritmo de simplificación de balances (quién le debe a quién) puede tener edge cases con ciclos de deuda (A→B→C→A). Mitigación: cubrir con tests unitarios desde la Fase 4.
- **Invitación por email**: resolver email → uid sin exponer la lista completa de usuarios registrados. Mitigación: Cloud Function callable, nunca una query directa desde el cliente.
- **Costo de Firebase Blaze**: Cloud Functions programadas + lecturas de Firestore pueden crecer con más usuarios/grupos activos. Mitigación: monitorear cuotas desde el inicio, igual que se hizo con el gym app.
- **Cálculo de balance en tiempo real**: si un grupo crece mucho (muchos movimientos), calcular el balance en el cliente en cada lectura puede volverse lento. Mitigación: si se vuelve un problema, mover el cálculo a una Cloud Function que mantenga un documento de balance cacheado por grupo.
- **Node.js 20 en Cloud Functions se desactiva el 30 de octubre de 2026**: hay que migrar el runtime de `functions/` a Node 22 antes de esa fecha, o los deploys dejarán de funcionar. No urgente todavía (detectado en septiembre 2026), pero no dejarlo para el último momento.
- **`auth.ts` usa `BehaviorSubject` en vez de un signal**, la única pieza de la app que no sigue el patrón reactivo (signals + `effect()`/`toSignal()`) del resto del código. No causa bugs hoy (irónicamente, `BehaviorSubject` + `async` pipe sí dispara change detection correctamente en la app zoneless), pero es una inconsistencia arquitectónica identificada durante la auditoría del bug de change detection de la Fase 7 (modo claro) — vale la pena unificarlo si se vuelve a tocar ese archivo.
- **`GroupsService.remove()` no valida `recurringPayments`**: solo chequea `movements`/`settlements`/`goalEntries` antes de permitir borrar un grupo (ver DATABASE.md, "Balance de grupo y abonos") — un grupo con pagos recurrentes de grupo activos (`RecurringPayment` con `groupId`) puede borrarse sin aviso, dejando esos docs huérfanos (`groupId` apuntando a un grupo que ya no existe; `processRecurringPayments` seguiría procesándolos indefinidamente). Detectado al escribir `scripts/delete-group.mjs` (que sí los limpia). Mitigación: agregar el mismo chequeo de `recurringPayments` a `remove()` cuando se vuelva a tocar ese flujo.
